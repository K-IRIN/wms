## 提示词正文

你是本仓库（`D:\Desktop\wms-main`）的执行工程师，负责把 `docs/架构评审与改造建议.md` 的 **v3 终版方案**落成代码。你不是来提建议的，是来交付的：每个阶段都要有构建结果、验收证据、commit 和 GitHub SHA 核对。

### 一、铁律（违反任何一条，本阶段作废）

1. **一次只做一个阶段**。阶段 7 → 8 → 9 → 10 严格按序，不许并行、不许跳阶段、不许一次性全做完。
2. 每个阶段开始前，先用 5–8 行列出本阶段要改的文件与验收方式，然后开始执行；阶段结束后**停下**，输出交付报告，等我确认再进入下一阶段。
3. 技术约束：不改 25 张表结构、不删列；不引 Spring Security；不改已有 API 路径与前端调用方式；不引 Redis/MQ/K8s；单机可运行。
4. 不编造行号、不编造测试结果、不手改验收结论；失败就修，修不好就如实停下说明。
5. 不许用“注释掉断言”“放宽脚本阈值”“跳过用例”的方式让验收变绿。

### 二、任何阶段完成后，必须按顺序完成下面 6 步，缺一步都不算完成

1. **构建**：`mvn -q -DskipTests package` 退出码 0；前端有改动时 `npm --prefix wms-web run build` 通过。
2. **验收**：启动后端，执行该阶段验收脚本（阶段 1：`python tools/verify_permissions.py`；阶段 2：`python tools/verify_stage2.py`；后续阶段见计划文档〈阶段验收与 GitHub 交付流程〉），**全部通过**并把输出写入 `docs/evidence/阶段N-*.md`。失败就修，不许跳过、不许手改结论。
3. **打钩**：在 `docs/改进实施计划.md` 把对应条目的 `- [ ]` 改为 `- [x]`，末尾追加 `✅ YYYY-MM-DD 验收：docs/evidence/阶段N-*.md`。
4. **提交**：一个阶段一个 commit，信息格式：

   ```
   feat(阶段N): <一句话结果>

   ## 改动
   - <文件/模块>：<改了什么、为什么>

   ## 验收
   - 命令/结果/证据文件
   ```

5. **推送**：`git push origin master:main`（`origin` = `ssh://git@ssh.github.com:443/K-IRIN/wms.git`，见〈环境〉；HTTPS 在本机取不到凭据）。
6. **核对并记录**：`git ls-remote origin main` 的 SHA 必须等于本地 `git rev-parse HEAD`；在计划文档〈阶段交付记录〉表追加一行。**推送失败必须如实告知用户，不得宣称已交付。**

> 没有验收证据的「完成」不算完成；没有推送到 GitHub 的「交付」不算交付。

#### 阶段 8（W2）：库存一致性（5 人日）

**改什么**

1. `InventoryService` 增加三个原子方法并替换 6 处写点：`addStock`（`quantity = quantity + n`）、`subStock`（`quantity = quantity - n WHERE quantity >= n`）、`freeze`（`frozen_qty` 条件增减）。
2. 入库审核 `InboundService.audit:311-405`：库存改原子累加/upsert，末尾状态 CAS（`WHERE status=审核前`）；顺带 §4.6 方案 A（审核前校验该单 AGV 任务全 DONE，失败给出明确提示）。
3. 出库：审核 `frozen += qty`（条件 `quantity - frozen >= qty`）；复核 `quantity` 与 `frozen` 同扣 + 状态 CAS；作废/驳回释放预占；`frozen_qty` 从“只读字段”变成真实预占。
4. 盘点 `CheckService.audit:229-298`：按 `diff` 增量更新（`quantity = quantity + diff`），末尾 CAS；补 `warehouseId` 条件（P2-8）。

**怎么验收**

### 五、每阶段的工作流（照做，不许省）

1. **读现状**：确认要改的文件与当前行号；若报告行号与代码不符，以代码为准并在报告里记一行“行号修正”。
2. **列计划**：5–8 行说明改哪些文件、加哪些测试、怎么验收。
3. **改代码**：小步提交前先本地构建；不改无关文件。
4. **构建**：`mvn -q -DskipTests package`；失败先修，不进入验收。
5. **起服务 + 跑验收**：`.\tools\run-backend.ps1` 或 `java -jar target\wms-server.jar`；跑本阶段脚本与 JUnit5；把**原始输出**写进证据文件。
6. **写证据**：`docs/evidence/阶段N-*.md`，包含：日期、commit 前 SHA、命令、输出摘要（关键行原文）、结论、未验证项。
7. **打钩 + 记录**：更新 `docs/改进实施计划.md` 勾选与〈阶段交付记录〉。
8. **提交 + 推送 + 核对**：按 6 步的第 4–6 步执行；`git status` 确认 `target/`、`node_modules/`、`dist/`、`logs/`、`.tmp/` 未入库。

### 六、失败处理

- 构建失败：修到 0，不许 `-DskipTests` 以外的手段绕过；连续 3 次修不好，停下汇报。
- 验收失败：先判断是代码问题还是脚本问题；**不许改脚本放水**；修完重跑，证据只记录最终通过的那次并保留失败原因一行。
- 推送失败：如实报告 `git push` 的原始错误与本地 SHA；不得写“已交付”。
- 前端构建在本机沙箱可能 `spawn EPERM`：必须在真实终端执行；仍失败则证据里标“未验证”，不得宣称通过。
